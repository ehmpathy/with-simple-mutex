## the outcome world

### day-in-the-life

a developer has two integration test suites that both touch one shared external account (the motivating case: a shared proxy-phone provider). run them at the same time — two separate processes on the same CI machine — and they collide: one suite mutates the account while the other reads it, and both flake.

with `with-simple-mutex` in place, they wrap the critical section once. because the two suites are **separate processes**, the lock must reach across processes → a per-machine (on-disk local) cache, not per-process in-memory:

```ts
import { createCache } from 'simple-on-disk-cache';
import { withSimpleMutex } from 'with-simple-mutex';

const genProxyPhone = withSimpleMutex(
  async (input: { phone: string }) => doTheWork(input),
  {
    key: (input) => `proxy-phone.${input.phone}`,
    cache: createCache({ directory: { local: { path: '/tmp/locks' } } }), // per-machine
  },
);

const result = await genProxyPhone({ phone: '+14632270513' });
```

now callers that share a key take turns. same key → serialized. different keys → parallel. the collision is gone, and the fix was one wrapper.

> the cache choice is not incidental: **per-process in-memory would not fix this case** — two test processes have two separate in-memory stores. the isolation tier must match the collision's blast radius. this is exactly the "pick your tier by picking your cache" decision made concrete.

then the aha lands: to widen the lock from "this process" to "this machine" to "every machine on earth", they leave **the call untouched** — they only swap the cache:

| cache                                 | isolation scope        |
| ------------------------------------- | ---------------------- |
| simple-in-memory-cache                | per-process            |
| simple-on-disk-cache (local disk)     | per-machine            |
| simple-on-disk-cache (cloud disk, s3) | global / cross-machine |

### before / after

| dimension        | before                                              | after                                               |
| ---------------- | --------------------------------------------------- | --------------------------------------------------- |
| shared-resource races | hand-rolled flags, sleeps, "hope it settles"   | one wrapper, correct by construction                |
| scope change     | rewrite the locking mechanism                       | swap the cache; call is identical                   |
| correctness      | check-then-set (two ops → double-winner window)     | atomic conditional write (exactly one winner)       |
| stalled holder   | silently runs on unprotected                        | fails fast with `SimpleMutexLeaseExpiredError`      |

### the "aha" moment

> "the only piece that changes across process / machine / global is the cache i pass in."

that is the whole pitch. the lock's power tier is a property of the backend, not of the lock code. pick the tier by picking the cache.

## user experience

### usecases & goals

- **prevent races** — serialize access to a shared resource that has no lock of its own (shared test account, shared file, shared api quota).
- **run exactly once** — de-dupe work across a fleet: one cron, one migration, one leader.
- **guard side effects** — enforce one holder where a db transaction can't reach: one email, one charge.

### contract they leverage

```ts
withSimpleMutex<TInput, TOutput>(
  logic: (input: TInput) => Promise<TOutput>,
  options: {
    key: (input: TInput) => string;
    cache: WithCacheConditionals<SimpleCache<string>>;
    lease?: { duration?: IsoDuration };                          // default { minutes: 30 }
    acquire?: { timeout?: IsoDuration; interval?: IsoDuration };
  },
): (input: TInput) => Promise<TOutput>
```

| field              | required | default           | role                                                     |
| ------------------ | -------- | ----------------- | -------------------------------------------------------- |
| `key`              | yes      | —                 | getter for lock key from input; same key → serialized    |
| `cache`            | yes      | —                 | any `WithCacheConditionals<SimpleCache<string>>`         |
| `lease.duration`   | no       | `{ minutes: 30 }` | how long you hold the lock; rival may steal once expired |
| `acquire.timeout`  | no       | — (wait forever)  | max wait to acquire before `SimpleMutexAcquireTimeoutError` |
| `acquire.interval` | no       | `{ seconds: 1 }`  | poll interval between acquire attempts                   |

outputs:
- on success → whatever `logic` returns, unchanged (`TOutput`), lock released.
- on acquire-timeout → throws `SimpleMutexAcquireTimeoutError`.
- on lost lease mid-work → throws `SimpleMutexLeaseExpiredError` (fail fast: the *wrapper* rejects promptly at the deadline; note it cannot cancel `logic`'s in-flight side effects — see cluster B caveat 2, lease-lock-not-fenced-lock).

### what leverage looks like

- **dynamic per-input lock** — `key: (input) => `proxy-phone.${input.phone}`` → one lock per phone.
- **single global lock** — `key: () => 'migration'` → every caller serializes through one lock.
- **bounded wait** — `acquire: { timeout: { seconds: 30 }, interval: { seconds: 1 } }` → give up rather than wait forever.
- **long critical section** — `lease: { duration: { minutes: 30 } }` → size lease above worst-case runtime.

### timeline a caller goes through

1. call the wrapped fn with input.
2. derive key from input.
3. **acquire** — put-if-absent; if held, poll on `acquire.interval` until free, or throw on `acquire.timeout`.
4. **hold** — run `logic` raced against a **local lease-deadline timer** (`Promise.race`); if the lease elapses before `logic` finishes → fail fast with `SimpleMutexLeaseExpiredError`. *(v1 has no heartbeat — a single up-front lease; the timer is a local clock, zero cache reads. see cluster B.)*
5. **release** — compare-and-delete: remove the key only if the version is still ours; return `logic`'s result.

## mental model

### how a user describes it to a friend

> "it's a `with...` wrapper — you hand it your async function and a key, and it makes sure only one call per key runs at a time. want the lock to span more machines? give it a bigger cache. that's it."

### analogies / metaphors

- **the single-key restroom** — one key on the wall. you take it, you're in; others wait for the key to come back. the lease is the "auto-flush after N minutes so a passed-out occupant doesn't lock everyone out forever."
- **a talking stick** — only the holder speaks (runs); it passes on, never duplicates.
- **conference-room booking** — the booking (lease) has an end time; overrun it and someone else can legitimately claim the room.

### terms: theirs vs ours

| they say            | we say                        |
| ------------------- | ----------------------------- |
| "lock" / "mutex"    | mutex, lock                   |
| "the locked code"   | critical section              |
| "how long i hold it"| lease (`lease.duration`)      |
| "how long i'll wait"| acquire timeout               |
| "someone took over" | steal an expired lease        |
| "my claim tag"      | version (etag) on the lock    |

we deliberately keep **lease** (not "ttl" — the older proposal's word; readme retired it) and **acquire** (not "wait"), because they name the two independent time budgets precisely.

## evaluation

### how well it solves the goals

- **prevent races** — ✅ strong. atomic acquire → exactly one winner, no check-then-set window.
- **run exactly once** — ✅ strong for the common case; ⚠️ "exactly once" degrades to "at least once, rarely twice" under a pause longer than the lease (see cons).
- **guard side effects** — ✅ good, with honest limits: on lease loss the wrapper fails fast (the caller learns promptly), but it is a lease lock not a fenced lock — it cannot force a stalled holder's in-flight side effects to stop (cluster B caveat 2). contention is made safe and rare, not impossible under arbitrary pauses.

### pros

- **one primitive, three tiers** — scope chosen by cache, call unchanged. this is the headline value.
- **correct by construction** — correctness rests on the cache's atomic conditional write, not on timing/sleeps.
- **pit-of-success typing** — a non-conditional cache **won't compile**. a lock without atomic writes is not a lock; the type system enforces it.
- **fail-fast on lost lease** — no silent unprotected execution; `SimpleMutexLeaseExpiredError` surfaces the hazard.
- **tiny surface** — a `with...` wrapper consistent with the ehmpathy `withSimpleCache` family; low learning cost.

### cons / honest limits

- **lease lock, not fenced lock** — no monotonic fencing token, so it cannot defend a downstream store against a stalled-then-resumed holder. it makes contention *safe and rare*, not *impossible under arbitrary pauses*.
- **lease sizing is the caller's burden** — too short → premature steals; too long → slow recovery after a real crash. default `{ minutes: 30 }` is safe-ish but rarely optimal.
- **correctness is only as atomic as the backend** — the guarantee is inherited. a backend whose "conditional write" is not truly atomic silently downgrades the lock. *(all three shipped backends provide genuine atomic conditionals — in-memory CAS, on-disk O_EXCL/rename, s3 If-None-Match/If-Match — verified in groundwork.)*

### edgecases & how the contract keeps users in the pit of success

| edgecase                          | contract behavior                                                                 |
| --------------------------------- | --------------------------------------------------------------------------------- |
| two callers race to acquire       | atomic put-if-absent → exactly one wins; loser polls or times out                 |
| holder crashes mid-work           | native cache `expiration` auto-evicts the stale lock; next put-if-absent reclaims it; no manual cleanup, no CAS-steal (v1) |
| holder stalls past lease          | the local lease-deadline timer fires → fail fast with `SimpleMutexLeaseExpiredError` (no heartbeat needed) |
| rival arrives while lease is live | the key is still present (not yet expired) → rival's put-if-absent fails; it polls or times out |
| caller passes a plain cache       | **compile error** — `WithCacheConditionals` not satisfied                         |
| `logic` throws                    | lock released; error propagates (must not be swallowed as a lock failure)         |
| never acquires                    | with `acquire.timeout` → typed throw; without → waits (documented, deliberate)    |

### decision clusters (the wisher calls, grouped to decide together)

the seven questions are not independent — they collapse into four coupled decisions:

- **cluster A — dependency & scope** (Q1 + Q4): **[resolved ✅ 2026-07-23]** — both halves settled. dependency: all three backends shipped conditionals, `with-simple-cache@0.17.0` is a direct dep, the mutex is unblocked. scope: **full — all three tiers (in-memory + on-disk-local + s3-global), no deferrals** (s3 confirmed shipped in `sdk-aws-s3@0.2.0`).
- **cluster B — lease mechanism** (Q5 + Q6): **[decided ✅ 2026-07-07]** — v1 uses native `expiration` for auto-evict and drops the heartbeat. no mid-work renew, no manual CAS-steal; a lapsed lease is reclaimed by plain put-if-absent. manual steal + heartbeat deferred to v2.
  - *consequence:* the holder must finish within one `lease.duration` (no renew to extend it). but mid-work fail-fast is **still preserved** without a heartbeat — a `Promise.race([logic(), leaseTimer])` against a **local** lease-deadline timer fires `SimpleMutexLeaseExpiredError` the moment the lease lapses, with zero cache reads. the timer is the *fail-fast* half; the heartbeat (deferred to v2) is the *extend* half — two different jobs. what v1 loses is lease *extension*, not mid-work abort.
    - *caveat 1 (clock skew):* the local timer and the cache's native `expiration` run on different clocks. the key becomes stealable at `cacheWrite + expiration`; our timer starts at acquire-return (≈ `cacheWrite + latency`). to avoid a brief unprotected window, fire the local timer **at or before** the cache-TTL point (e.g. timer = `lease.duration − margin`, or set the cache `expiration` slightly above `lease.duration`). the timer is a *conservative* trigger — past the deadline we cannot guarantee exclusivity, so abort is correct even if no rival has actually taken the key yet.
    - *caveat 2 (the race does not cancel `logic`):* `Promise.race` decides which promise settles first; it does **not** terminate the loser. when the lease timer wins, the wrapper throws `SimpleMutexLeaseExpiredError`, but `logic()` **runs on** with its side effects — JS promises are not cancellable. so the race makes the *wrapper* fail-fast, not the *work*. this is precisely why the lock stays a **lease lock, not a fenced lock** (readme `notes`): a stalled-then-resumed holder's writes are not fenced. the only way to actually stop the inner work is **cooperative** abort — thread an `AbortSignal` into `logic` so it can bail at its own checkpoints — which is opt-in and requires `logic` to honor it. *(this reinforces Q7: whether/what we thread into `logic` — an `AbortSignal` is a candidate second arg alongside or instead of `context`.)*
- **cluster C — cache contract shape** (Q2 + Q3): **[resolved ✅ 2026-07-23]** — adopt the *shipped* shape from `with-simple-cache@0.17.0`: `version(key)` + `condition: { version: string | null }` on get/set, throwing `SimpleCacheConditionError`. this superseded both the readme's and #57's sketches; the mutex conforms to what actually shipped.
- **cluster D — signature** (Q7): **[decided ✅ 2026-07-23]** — single-arg `logic: (input) => Promise<TOutput>` for v1 (context via closure); `AbortSignal` second arg is a backward-compatible v2 widening.

*decided cut (2026-07-23):* A → **resolved** (deps live, unblocked); v1 scope = **full — all three tiers, no deferrals** (in-memory + on-disk-local + s3-global, all conditionals-shipped). B → native-expiry, no heartbeat. C → **shipped shape** (`version(key)` + `condition`, `SimpleCacheConditionError`). D → single-arg logic. **every load-bearing decision is settled; the vision is ready to drive into execution.**

### execution notes surfaced in self-review (not wisher blockers, but must not be lost)

- **key-safety** — the on-disk backend rejects special characters in keys (`assertIsValidOnDiskCacheKey` throws `InvalidOnDiskCacheKeyError`); yet the readme's flagship key `proxy-phone.+1463...` contains `+`/`.`. the mutex must cast the caller's key to a safe key internally (see `castToSafeOnDiskCacheKey`) so callers keep human-readable keys without a throw.
- **uuid is a devDep** — the lock token needs a runtime uuid, but `uuid-fns` sits in `devDependencies` (`package.json:106`). move it to `dependencies`, or use `crypto.randomUUID`, before publish.
- **release-failure order** — a release that fails *after* `logic` succeeded must not mask a good result. *(the original "log it, do not throw over the return value" wording is superseded 2026-07-25 by a wisher decision + `rule.forbid.failhide`: `delMutexLock` already absorbs the one EXPECTED miss (a rival owns the key) as a safe no-op, so every fault that reaches the wrapper is UNEXPECTED — and the failhide mega-blocker forbids a log-and-drop of an unexpected error. the wisher confirmed the more useful contract: a surfaced release fault lets the caller **retry to clear the lock**. so on the success path the unexpected release fault **propagates**; on the failure path logic's own error stays PRIMARY — carried as the `cause` of a combined fault that also names the release fault, neither hidden. "must not mask a good result" is still honored: a clean release returns the result unchanged, and correctness stays safe regardless since the key lapses with the lease.)*
- **single-key scope** — one call locks one key; multi-resource lock order is a separate, larger primitive, deliberately out of scope for the mvp.

- **[resolved ✅ 2026-07-23]** — s3 conditional-write primitives are shipped. `sdk-aws-s3@0.2.0` implements put-if-absent (`condition: { etag: null }`) and compare-and-set, throwing `S3PreconditionFailedError`; `simple-on-disk-cache@1.8.1`'s cloud tier surfaces + reconciles the etag as its version token (`reconcileCloudPreconditionFailure`, `setToAdapterConditional`). the earlier concern ("the s3 adapter does not surface etag/version") no longer holds — the global tier is fully viable and in scope (Q4).

> - ~~**heartbeat on s3 is a cost few expect**~~ → moot: cluster B dropped the heartbeat entirely for v1 (single up-front lease).

design tensions that persist (not cleared by the deps — inherent to a lease lock):

- **two time budgets to reason about.** `lease.duration` and `acquire.timeout` are independent and both easy to mis-size. the defaults help (`lease` defaults, `acquire` waits forever), but "why did my lock get stolen?" will be a support question. good errors mitigate, they don't eliminate.
- **lease lock, not fenced lock.** the wrapper fails fast on lease loss but cannot cancel a stalled holder's in-flight side effects (JS promises are not cancellable; cluster B caveat 2). contention is made safe and rare, not impossible under arbitrary pauses. the `AbortSignal` cooperative-cancel path is a deliberate v2, not v1.
- **lease duration is the caller's burden — but a *loud* one, not a silent one.** with no heartbeat (v1), the holder must finish within one `lease.duration`; too short → premature reclaim, too long → slow recovery after a real crash. the default `{ minutes: 30 }` is safe-ish but rarely optimal for a given critical section. *what keeps this from being a footgun: a lease over-run is never silent — it throws `SimpleMutexLeaseExpiredError`, a clear typed signal that tells the caller to raise `lease.duration` or shorten the section.* this is why the default stays **optional with a finite value** rather than **infinite** (an infinite lease is the real trap: a crashed holder would deadlock the key forever, with no signal) or **required** (a sensible default beats a forced up-front guess from every caller, since the error corrects a wrong guess loudly).
